## Findings priorizados

### P1 — Studio: mutação visual retornava HTTP 400 no desktop — RESOLVIDO NO R-2

- **Causa reproduzida:** a UI já enviava o payload CAS correto (`components` + `expected_version`), mas a evidência original foi executada contra um processo backend stale, anterior ao contrato CA-4; esse processo rejeitava `expected_version` como campo desconhecido. O código atual do handler aceita o campo e mapeia conflito real para HTTP 409.
- **Correção/prova:** backend recompilado a partir do commit atual; o mesmo payload reproduzido (`expected_version: 17`) retornou HTTP 200 e avançou o projeto para a versão 18. O roteiro `app/ui/app/e2e/capture_studio_evidence.mjs` agora falha se a mutação visual não retornar exatamente 200.
- **Evidência nova:** `docs/evidencias/screen-r2-studio-edit-desktop.png`, `docs/evidencias/screen-r2-studio-edit-mobile.png` e a entrada correspondente em `docs/evidencias/browser-console-audit.json`, com `consoleErrors: []`, `httpFailures: []` e `errorsCount: 0`.
- **Gates:** `go test ./internal/agent ./server -run 'Studio|Builder|Visual|CAS|Version' -count=1` passou; E2E Playwright desktop `1440x900` e mobile `390x844` passou sem HTTP 400.

### P1 — Egress zero-trust não estava demonstrado em todos os caminhos de saída do servidor — RESOLVIDO NO R-1

- **Causa:** a auditoria encontrou clientes crus/default em `server/cloud_proxy.go`, `download.go`, `agent_planner_resolver.go`, `agent_routes.go`, `routes.go`, `images.go`, `model_recommendations.go` e `model_show_cache.go`.
- **Correção aplicada:** foi criado `server/egress_client.go`, que centraliza o transporte em `internal/agent.NewSafeEgressHTTPClient`, com proxy ambiental desabilitado, resolução/pinning de IP, bloqueio SSRF, redirects controlados e limites/DLP do transporte. Os callsites de proxy, download, planner, rotas de agentes, rotas gerais, imagens, recomendações e cache de modelo foram migrados. Loopback só é permitido quando a configuração local o declara explicitamente; fixtures `httptest` usam clientes/dialers de teste explícitos.
- **Prova:** `git grep -nE "http.DefaultClient|&http.Client\{|http.Get\(|http.Post\(" -- server` retorna somente construções de clientes em `server/model_recommendations_test.go`, todas restritas a transports mockados de teste; não há cliente HTTP cru em código de produção server-side. `go test ./server -run 'Egress|SSRF|Proxy|Download|Planner|ZeroTrust|DLP|Server' -count=1`, `go build ./...` e `go test ./internal/agent ./server -count=1` passaram.
- **Limite honesto:** o smoke externo contra upstream autorizado e a semântica DLP específica de cada payload continuam condicionados a credenciais/serviços externos; isso não é declarado como validado aqui.

### WIN-1 — build sem CGO e cross-build Windows — RESOLVIDO LOCALMENTE

- **Causa reproduzida:** os arquivos MLX/xgrammar e o webview desktop dependiam de CGO/native runtime; sem CGO o pacote `mlx` expunha símbolos ausentes, o app desktop materializava o pacote `store` indevidamente no Linux e Git usava `os.DevNull`, incompatível com Git for Windows.
- **Correção:** implementados build tags `cgo` para os caminhos nativos e fallbacks `!cgo` explícitos para MLX, xgrammar, gerador e webview. Os fallbacks retornam `MLX indisponível`/`xgrammar indisponível` e nunca simulam execução nativa. O wrapper desktop só é incluído em Windows/macOS. `GIT_CONFIG_SYSTEM=` e `GIT_CONFIG_GLOBAL=` desabilitam configurações externas sem depender de `/dev/null`/`NUL`.
- **Prova local:** `CGO_ENABLED=0 go build ./...` e `GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build ./...` passaram; `go build ./...`, `go test ./internal/agent ./server`, contratos e integrity também passaram.
- **CI:** foi adicionado o job `platform-builds` em `.github/workflows/class-a-plus-integrity.yaml`, com os dois builds obrigatórios. A confirmação remota fica pendente até os runs do commit WIN-1 concluírem.
- **Limites honestos:** isto prova compilação cruzada, não execução em Windows físico, disponibilidade de MLX/WebView nativos, DACL real ou smoke de instalador assinado.
